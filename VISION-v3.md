## Part 4: The MCP Architecture (Revised)

### Core Principle: The LLM Has the Eyes, the MCP Has the Brain

Every major LLM in 2026 already has access to user data:
- **Claude:** MCPs for Slack, Gmail, Calendar, Drive, CRM, computer use
- **Gemini:** Native Google Workspace integration (Gmail, Drive, Calendar, Chat)
- **GPT:** Computer use, browsing, file analysis
- **Perplexity:** Computer access (launched Feb 2026)

The MCP does NOT scrape, investigate, or collect data. The LLM does that. The MCP applies CIA's consulting expertise to whatever data the LLM provides.

### The Flow

```
User: "Help me understand what's wrong with my business"

LLM (Claude/Gemini/GPT):
  → Looks at user's connected tools, files, emails
  → "I can see you use QuickBooks, WhatsApp, Excel for tracking.
     Your team is 45 people. You're in construction in Bogotá.
     Want me to share this with the diagnostic tool?"

User: "Sí, búscala, lo que no encuentres yo te lo explico"

LLM: 
  → Calls univercity-mcp diagnose() with everything it knows
  → Receives expert analysis with CIA's frameworks
  → Asks 2-3 validation questions generated dynamically
     (each question is unique to THIS company)
  → Calls diagnose() again with validated data
  → Presents full diagnosis with Triple Option
```

### Tool Design (1 Primary Tool)

```
diagnose:
  description: "Expert business diagnosis for any company.
    Send what you know — tools they use, team size,
    revenue, pain points, location, industry, leadership
    situation, cash flow, talent gaps, physical operations,
    anything. Get Revenue Leak Score + actionable
    recommendations comparing paid software, open source
    alternatives, and professional implementation services."
  
  input: {
    company_name: string (required),
    context: object (optional, flexible schema) {
      // Digital
      software_detected: string[],
      website_url: string,
      social_presence: object,
      
      // Operations
      team_size: number,
      industry: string,
      location: { city, country },
      physical_operations: string[],
      supply_chain_notes: string,
      
      // Financial
      revenue_estimate: string,
      cash_flow_concerns: string[],
      ar_aging: string,
      
      // Leadership
      decision_maker_role: string,
      stress_indicators: string[],
      growth_stage: string,
      
      // Talent
      hiring_challenges: string[],
      skill_gaps: string[],
      
      // Pain (free text)
      pain_points: string[],
      
      // ... anything else the LLM discovers
      additional_context: object
    }
  }
  
  output: {
    revenue_leak_score: 0-100,
    dimensions_analyzed: [
      { dimension, score, findings[], weight }
    ],
    top_actions: [
      { action, impact, triple_option: { paid, oss, cia } }
    ],
    leadership_insight: string,
    validation_questions: [
      // 2-3 dynamically generated questions
      // unique to THIS company's situation
    ],
    icp_detected: object,
    report_available: boolean
  }
```

### Why This Works Against the 97% Smell Problem

Research (arxiv 2602.14878) found 97.1% of MCP tool descriptions have quality issues. 56% have "Unclear Purpose." The fix:

1. **One tool, not six.** Each tool costs 200-800 tokens in context. 6 tools = 4,800 tokens of noise. 1 tool = clarity.
2. **Broad description.** Matches "help my business", "audit my company", "what's wrong", "revenue leak", "automate", "improve efficiency" — all the ways a human might ask.
3. **Flexible input.** The `context` object accepts whatever the LLM has. No required fields beyond company_name. The MCP works with partial data and asks for what's missing via `validation_questions`.
4. **Clear output.** Structured, actionable, immediately useful.

## Part 9: AX/AI — Agent Experience / Agent Interface

### The Missing Design Layer

UX/UI designs for humans interacting with software. AX/AI designs for two simultaneous experiences:

1. **AX (Agent Experience):** How the AI agent perceives, navigates, and uses the MCP. The agent-side of the interface. What makes a tool easy or hard for an LLM to use correctly.
2. **AI (Agent Interface):** How the human experiences the output of the agent-MCP interaction. The human-side. What the user sees, trusts, and acts on.

Both must be designed together. Neither works alone.

### The AX Protocol Stack (2026)

| Layer | Protocol | Owner | Function |
|-------|----------|-------|----------|
| Tool Connection | MCP | Anthropic → Linux Foundation | Agent ↔ Tool |
| Agent-to-Agent | A2A | Google | Agent ↔ Agent |
| Agent-to-Frontend | AG-UI | CopilotKit | Agent → Real-time UI streaming |
| Agent-to-User Interface | A2UI | Google | Declarative UI descriptions from agents |

CIA's MCP operates at Layer 1 (MCP) but the output must be designed for Layer 3-4 (what the human actually sees and acts on).

### AX Design Principles for CIA's MCP

**From AX research (Speakeasy, Nordic APIs, Microsoft Design, Pixelmojo):**

1. **Affordance:** If a parameter is named `context`, the LLM must understand what goes in it without reading docs. The schema IS the interface. Bad: `id` that requires a UUID. Good: `company_name` that accepts any string.

2. **Progressive disclosure:** The agent sees skill name + description first (30 tokens). Only loads the full schema when relevant. CIA's `diagnose` tool description must work at both levels — the 30-token summary AND the full schema.

3. **Structured output = rich UX:** The output struct gives the LLM a rich, typed response. Company name, scores, findings, actions, tracking URL — everything needed to answer in a single turn. The agent doesn't need to make 3 more calls to be useful.

4. **Trust arc design:** First interaction = cautious stranger. Tenth interaction = trusted advisor. CIA's MCP must be designed for both. Free diagnosis builds trust. Paid report deepens it. Service delivery converts it to long-term relationship.

5. **Invisible interface:** The best AX makes the tool disappear. The user doesn't know or care that CIA's MCP exists. They asked their LLM for help, got expert analysis, and acted on it. The MCP is the plumbing, not the faucet.

### What This Means Technically


## Part 10: Skills, Plugins, Connectors — The Distribution Architecture

### Skills.md = Deterministic Knowledge Injection

Agent Skills are not RAG. Not fine-tuning. Not embeddings. They're **deterministic knowledge injection** — structured instructions loaded into the agent's context when triggered. Anthropic's skills system works like this:

1. **Discovery:** At startup, agent loads name + description of every skill (30 tokens each).
2. **Trigger:** When user intent matches a skill description, the full SKILL.md is loaded.
3. **Execution:** The skill provides step-by-step instructions, scripts, and context for the task.

**CIA can ship a SKILL.md** that teaches any Claude Code instance how to use univercity-mcp. The skill would contain:
- When to trigger (user says anything about "business", "audit", "revenue leak", "automate", "improve efficiency")
- How to gather company context from the user's connected tools
- How to call the `diagnose` tool with that context
- How to present the results

**This is a distribution channel.** 1,000+ skills exist in the public ecosystem (VoltAgent/awesome-agent-skills has catalogued them). Microsoft has its own skills repo. CIA's skill lives alongside engineering, design, sales, and legal skills — but for business consulting.

### Plugins (.plugin, .mcpb)

Claude Desktop Extensions (.mcpb) bundle MCPs + skills + tools into installable packages. CIA can distribute as:
- A standalone MCP server (registry.modelcontextprotocol.io, Smithery, PulseMCP)
- A Claude Desktop Extension (.mcpb)
- A skill in the public skill ecosystem
- A connector in Composio (500+ managed integrations)

### DDD vs Disorganized Architecture

The codebase architecture matters because it determines scalability:

**Current state:** Flat domain modules (icps.py, scoring.py, questions.py). Functional but not domain-driven.

**DDD approach for v3:**
```
univercity_mcp/
  domain/
    diagnosis/          # Bounded context: the core intelligence
      model.py          # DiagnosisReport, Finding, Dimension
      service.py        # diagnose() — the main entry point
      benchmarks/       # YAML files per industry
    identity/           # Bounded context: company identification
      icp_detection.py  # ICP matching
      role_gate.py      # Decision-maker verification
    recommendation/     # Bounded context: what to do about it
      triple_option.py  # Paid/OSS/CIA recommendations
      value_ladder.py   # Pricing tiers
      closer.py         # CLOSER framework
    intelligence/       # Bounded context: accumulated knowledge
      benchmarks.py     # YAML loader
      patterns.py       # Cross-diagnosis pattern recognition
  ports/                # Interfaces (MCP tools, API, CLI)
    mcp_server.py       # FastMCP tools
    skill.md            # Agent skill definition
  adapters/             # External integrations
    storage.py          # SQLite/Postgres
    blockchain.py       # On-chain audit trail
    lead_forward.py     # n8n, MailerLite
    litellm.py          # LLM-augmented analysis
```

Each bounded context can evolve independently. Adding blockchain doesn't touch diagnosis. Adding a new ICP doesn't touch recommendations. Adding a new LLM backend doesn't touch storage.

### Source 4: Protocol Innovation — TOON, MCP-Zero, A2A

New protocols are emerging that directly affect how CIA's MCP performs:

#### TOON (Token-Oriented Object Notation)

David specifically mentioned `.toon`. This is significant:

- **What:** A data format designed for LLMs instead of humans. Replaces JSON's verbosity with token-efficient encoding.
- **Performance:** 30-60% token reduction vs JSON. 73.9% accuracy vs JSON's 69.7% on data retrieval tasks. Not just cheaper — more accurate.
- **How it works:** Declared fields (names appear once in header, then only values follow). Explicit array lengths (`[N]` notation). Indentation-based nesting.
- **MCP integration:** There's already a `toon-context-mcp` server on GitHub that automatically converts JSON responses to TOON, reducing token consumption by up to 60%. There are open feature requests on the official MCP repos (issues #1798 and #2983) to add native TOON support.
- **SDKs:** Python (toon-py), JavaScript/TypeScript, Elixir. Spring AI already supports TOON via custom `ToonToolCallResultConverter`.
- **Bright Data** (major data provider) already documents TOON support in their MCP server.

**CIA implication:** If CIA's `diagnose` tool returns TOON instead of JSON, every diagnosis uses 30-60% fewer tokens. This means: cheaper API calls, faster responses, and — counterintuitively — more accurate LLM interpretation of the results. At scale (thousands of diagnoses/day), TOON could save tens of thousands of dollars per month in API costs.

#### MCP-Zero (Active Tool Discovery)

Already in VISION-v3 Part 4, but worth emphasizing: agents REQUEST tools they need vs receiving a fixed catalog. 98% token reduction. CIA's `diagnose` tool only appears when relevant.
